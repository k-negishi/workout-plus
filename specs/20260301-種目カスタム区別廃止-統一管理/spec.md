# Feature Specification: 種目のプリセット/カスタム区別廃止・全種目統一管理

**Feature Branch**: `20260301-種目カスタム区別廃止-統一管理`
**Created**: 2026-03-01
**Status**: Draft
**Input**: User description: "https://github.com/k-negishi/workout-plus/issues/207"

## 背景・目的

現在アプリには「プリセット種目」と「カスタム種目」の区別（`is_custom` フラグ）が存在するが、ユーザーにとってポジティブな体験を生む場面がなく、プリセット種目の名称変更・削除ができないという **負の体験のみ** を生んでいる。

本機能は `is_custom` の概念を完全に廃止し、全種目を同等に扱えるようにすることで「引き算のデザイン」方針を体現する。また、削除済み種目と同名の種目を作成しようとした際の **復元フロー** も整備し、ユーザーの過去データへのアクセス性を保護する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全種目の編集・削除が可能になる (Priority: P1)

ユーザーが種目履歴画面（ExerciseHistoryFullScreen）を開くと、プリセット種目・カスタム種目を問わず、すべての種目に編集（名称変更）ボタンと削除ボタンが表示される。種目の出所による制限がなくなり、ユーザーは好きな種目の名前を変更したり不要な種目を削除できる。

**Why this priority**: 種目区別廃止の核心部分。ユーザーが直接体験する制約の解消であり、最も優先度が高い。

**Independent Test**: 種目履歴画面を開き、デフォルト（プリセット）種目に対して編集・削除ボタンが表示されることを確認することで独立してテスト可能。価値は「すべての種目が平等に管理できる」こと。

**Acceptance Scenarios**:

1. **Given** ユーザーが種目履歴画面を開いている、**When** 任意の種目（プリセット・カスタム問わず）を表示する、**Then** 編集（名称変更）ボタンと削除ボタンが必ず表示される
2. **Given** ユーザーがプリセット種目の編集ボタンをタップした、**When** 新しい名前を入力して保存する、**Then** 種目名が変更され、関連する履歴・PRにも反映される
3. **Given** ユーザーがプリセット種目の削除ボタンをタップした、**When** 削除を確認する、**Then** 種目は論理削除され、種目選択リストから除外される（履歴・PRは保持）
4. **Given** 旧バージョンから移行したデータが存在する、**When** アプリを起動する、**Then** 既存の全種目が制限なく編集・削除できる状態になっている

---

### User Story 2 - 削除済み種目の復元フロー (Priority: P2)

ユーザーが新規種目を作成しようとした際、以前に削除した種目と同じ名前を入力すると、アプリは「削除済みの種目として存在しています。復元しますか？」というダイアログを表示する。ユーザーは復元を選択することで過去の履歴・PRを持ったまま種目を再利用できる。

**Why this priority**: 削除済み種目と同名で新規作成すると過去データ（履歴・PR）が孤立してしまう問題を防ぐ。ユーザーの過去データ保護のため P2 に設定。

**Independent Test**: 種目を削除し、その後同名で新規作成しようとする操作フローをテストすることで独立して検証可能。価値は「過去のトレーニングデータを失わない」こと。

**Acceptance Scenarios**:

1. **Given** ユーザーが以前「ベンチプレス」を削除済みである、**When** 種目選択画面から「ベンチプレス」という名前で新規種目を作成しようとする、**Then** 「削除済みの種目 "ベンチプレス" があります。復元しますか？」というダイアログが表示される
2. **Given** 削除済み種目の復元ダイアログが表示されている、**When** 「復元する」を選択する、**Then** 種目が復元され、過去の履歴・PRが引き続きこの種目に紐づいた状態で利用できる
3. **Given** 削除済み種目の復元ダイアログが表示されている、**When** キャンセルする、**Then** ダイアログが閉じ、名前入力状態に戻る（重複した種目は作成されない）
4. **Given** 削除済みでない既存種目と全く同じ名前を入力した、**When** 作成ボタンをタップする、**Then** 既存種目との重複として扱われ、復元フローではなく通常の重複チェックダイアログが表示される

---

### User Story 3 - データ移行の透明性 (Priority: P3)

既存ユーザーがアプリをアップデートして起動したとき、バックグラウンドでデータ移行が自動実行され、`is_custom` フラグがすべての種目から取り除かれる。ユーザーは移行を意識することなく、更新後から即座に全種目が統一管理された状態で利用できる。

**Why this priority**: 既存ユーザーへの影響は自動処理されるため、ユーザー操作は不要。ただし移行の確実性が他ストーリーの前提となる。

**Independent Test**: アップデート前のデータベース状態をシミュレートし、起動後に全種目が問題なく操作できることを確認。

**Acceptance Scenarios**:

1. **Given** アップデート前のデータ（`is_custom` カラムが存在する旧スキーマ）、**When** アプリを起動する、**Then** 自動マイグレーションが実行され、全種目が正常に表示・操作できる
2. **Given** マイグレーション済みのデータベース、**When** アプリを通常操作する、**Then** 種目の追加・編集・削除・検索がすべて正常に動作する

---

### Edge Cases

- **削除済みかつ同名の種目が複数存在した場合**: 最新の削除日時を持つ種目を対象に復元フローを提示する（通常の操作ではこのケースは発生しないが、万一複数あれば最新削除分を優先）
- **復元時に同名の有効な種目がすでに存在する場合**: 復元フローには進まず、通常の重複ダイアログ（「同名の種目が既に存在します」）を表示する
- **マイグレーション失敗時**: アプリは前の状態にロールバックし、ユーザーデータを保持したまま起動を続ける
- **全種目が削除済みの状態から復元する場合**: 復元後の種目が正常に使用でき、ワークアウト記録にも追加できる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは全種目（出所問わず）に対して編集（名称変更）機能を提供しなければならない
- **FR-002**: システムは全種目（出所問わず）に対して削除（論理削除）機能を提供しなければならない
- **FR-003**: 種目の名称変更は、その種目に紐づくすべての履歴・PRに自動反映されなければならない
- **FR-004**: 削除は論理削除で行い、過去の履歴・PRに紐づくデータを物理削除してはならない
- **FR-005**: 新規種目の「作成」ボタンをタップした時点で、入力された名前が削除済み種目と完全一致する場合、システムは復元フローへ誘導しなければならない
- **FR-006**: 復元フローは「復元する」と「キャンセル」の選択肢を提供しなければならない
- **FR-007**: 「復元する」を選択した場合、過去の履歴・PRを保持したまま種目を有効状態に戻さなければならない
- **FR-008**: 既存ユーザーのデータは、アプリ起動時の自動マイグレーションによりデータ損失なく移行されなければならない
- **FR-009**: 削除された種目は、種目選択リストおよび種目検索から非表示でなければならない（論理削除の既存挙動を維持）

### Key Entities *(include if feature involves data)*

- **Exercise（種目）**: ユーザーが管理するトレーニング種目。名称・論理削除フラグ（`is_deleted`）を持つ。プリセット/カスタム区別は廃止
- **WorkoutExercise**: ワークアウトセッションと種目の紐づけ。種目が削除されても履歴として保持（外部キー整合性維持）
- **PersonalRecord（PR）**: 種目ごとの自己ベスト。種目が削除されても保持され、種目復元時に再利用可能

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 種目履歴画面を開いたとき、100%の種目に編集・削除ボタンが表示される（プリセット種目で非表示になるケースがゼロ）
- **SC-002**: 削除済み種目と同名の種目作成操作を行ったとき、100%のケースで復元ダイアログが表示され、データの孤立が発生しない
- **SC-003**: 既存ユーザーがアップデート後にアプリを起動したとき、データ損失なしにマイグレーションが完了する（完了率 100%）
- **SC-004**: 機能リリース後、「種目が編集できない」「なぜプリセット種目は変更できないのか」といった問い合わせ・フィードバックがゼロになる

## 前提条件・仮定

- 削除は引き続き論理削除（`is_deleted = 1`）で行い、外部キー整合性を維持する
- `ExerciseRepository.restore()` は実装済みと仮定する（Issue #207 記述に基づく）
- 復元フローで「新しく作成する」（別名で新規作成）オプションはスコープ外とする。「復元する」か「キャンセル」の2択とする
- 同名の削除済み種目が複数存在するケースは異常系として扱い、最新削除分を優先する

## スコープ外

- 「新しく作成する」（削除済みと同名で別IDの種目を強制作成する）オプション
- 種目の並び順カスタマイズ（別機能）
- 種目のカテゴリ・タグ管理（別機能）
- クラウド同期（別機能）
